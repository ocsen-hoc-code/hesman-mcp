**Hesman** — это MCP-сервер (Model Context Protocol) нового поколения, который даёт AI-агентам для программирования глубокое понимание вашей кодовой базы — символы, графы вызовов, зависимости и семантический поиск — и формирует ответы так, чтобы они стоили мало токенов: в этом репозитории `get_context` возвращает на 80–96% меньше токенов, чем весь файл, а списки вызывающих или ссылок на 66–72% короче обычного JSON (см. [Измерения на этом репозитории](#измерения-на-этом-репозитории)). Всё работает на вашей машине: без внешних API, без LSP-серверов, и ваш код никуда не отправляется.

## Зачем нужен Hesman?

AI-агенты для программирования мощны, но дороги. Каждая прочитанная ими строка кода стоит токенов. Отправлять файл целиком, когда агенту нужна одна функция, — значит впустую тратить контекст и деньги.

Hesman решает эту задачу так:

- **Отдаёт только то, что нужно агенту** — конкретную функцию, тех, кто её вызывает, то, что вызывает она, или символы, затронутые изменением.
- **Уплотняет и обрезает код** — `get_context` убирает комментарии и пустые строки и возвращает только строки вокруг точки фокуса, а не весь файл.
- **Компактные списки** — вызывающие, вызываемые, ссылки, символы и структура файлов приходят строками под именованными колонками, сгруппированными по файлам, с путями относительно проекта; ни одна строка не теряется. Ответ никогда не бывает больше своей исходной полезной нагрузки (см. [Конвейер сокращения токенов](#конвейер-сокращения-токенов)).
- **Работает на вашей машине** — никаких API-ключей, никакого внешнего сервиса и никаких задержек из-за него. Ваш код никогда не покидает вашу машину. Единственные загрузки — модель эмбеддингов при первом использовании и грамматики языков по запросу; и то и другое можно отключить (`--no-semantic`, `HESMAN_GRAMMARS_OFFLINE=1`).
- **Измеримая экономия** — каждый ответ инструмента, кроме `index_status`, содержит `_meta.reduction`, где точно показано, сколько токенов сэкономлено по сравнению с сырым выводом.

Итог: агенты работают быстрее, обходятся дешевле и рассуждают точнее, потому что видят нужный код, а не весь код.

## Быстрый старт

Пакета `hesman-mcp` пока нет в реестре npm, поэтому сейчас Hesman устанавливается из исходного кода:

```bash
# 1. Получите и соберите Hesman (Node.js ≥ 20)
git clone https://github.com/ocsen-hoc-code/hesman-mcp.git
cd hesman-mcp
npm install
npm run download:parsers
npm run build

# 2. Зарегистрируйте его в своих AI-клиентах (находит Claude Code, Cursor, VS Code, Codex, …)
node dist/index.js setup
```

Перезапустите клиент и откройте проект. `setup` записывает команду запуска, подходящую к способу установки Hesman (здесь — абсолютные пути к `node` и `dist/index.js`, так что в PATH ничего быть не должно); см. [Команда запуска](#команда-запуска).

После публикации пакета весь быстрый старт сведётся к одной строке:

```bash
npx -y hesman-mcp setup   # только после публикации hesman-mcp в npm
```

Сервер отвечает агенту сразу, а индексирует в фоне (несколько секунд для большинства проектов): все 11 инструментов работают с первой секунды, помечают результаты полем `_meta.indexing`, пока индекс ещё неполон, а `index_status` сообщает о ходе индексации.

## Возможности

### Понимание кода

| Возможность | Описание |
|---|---|
| **Поиск символов** | Находит функции, классы, методы по имени — точное, нечёткое совпадение или совпадение по префиксу (< 1 мс) |
| **Обход графа вызовов** | Проходит по вызывающим и вызываемым функциям на глубину до 3 уровней |
| **Отслеживание ссылок** | Находит все места использования символа в кодовой базе |
| **Анализ влияния** | Показывает, что сломается, если переименовать, удалить символ или изменить его сигнатуру |
| **Семантический поиск** | Опишите на естественном языке, что вы ищете, и найдите подходящий код |
| **Структурный поиск** | Находит шаблоны кода вроде `console.$METHOD($$$ARGS)` с именованными захватами |
| **Анализ зависимостей** | Показывает, что импортирует файл и кто импортирует из него |
| **Контекстные окна** | Возвращает сфокусированный, уплотнённый код вокруг любого места в файле |

### Конвейер сокращения токенов

Hesman сокращает токены тремя способами. Каждый ответ сообщает свою фактическую экономию в `_meta.reduction`, и ответ никогда не бывает больше своей исходной полезной нагрузки.

| Слой | Техника | Измеренная экономия | Применяется к |
|---|---|---|---|
| **Компактный режим** | Убирает комментарии, пустые строки, пробелы в конце строк | 0–16% от фрагмента кода, в зависимости от того, сколько в нём комментариев и пустых строк (`mode: "full"` против `"compact"`) | `get_context` |
| **Обрезка контекста** | Возвращает диапазон строк вокруг точки фокуса вместо файла | 96,0% при ±5 строках по умолчанию, 79,7% при ±40 строках (файл в 514 строк); 0%, когда запрошен весь файл | `get_context` |
| **Компактные списки** | Строки под именованными колонками, сгруппированные по файлам, пути относительно проекта | 66–72% для вызывающих, вызываемых и ссылок; 35–41% для списков символов, структуры файлов, зависимостей и анализа влияния | `find_symbol`, `get_references`, `get_callers`, `get_callees`, `get_file_structure`, `list_dependencies`, `impact_analysis` |

`find_pattern` и `semantic_search` возвращают исходную полезную нагрузку (`_meta.reduction: "0.0%"`). Числа получены на этом репозитории; полную таблицу и способ воспроизвести её см. в [Измерения на этом репозитории](#измерения-на-этом-репозитории). Поле `_meta.reduction` в каждом ответе показывает точную экономию для вашей нагрузки.

### Готов к продакшену

- **Пул воркеров** — параллельная индексация на ядрах CPU, размер по умолчанию подбирается автоматически
- **Отслеживание файлов** — инкрементальная переиндексация при изменении файлов с помощью chokidar
- **Корректное завершение** — дожидается активной работы, сбрасывает хранилища на диск, аккуратно останавливает воркеры
- **Индексация по хешу содержимого** — файлы разбираются заново, только когда их содержимое действительно изменилось
- **Поддержка монорепозиториев** — автоматически определяет рабочие пространства pnpm, lerna, nx, turbo и npm
- **Диагностика** — `hesman diag` выводит данные о памяти, статистику хранилищ, состояние пула и метрики кеша
- **Протестирован локально** — полный набор тестов, включая сквозные тесты через настоящий сервер, проходит на macOS; Linux и Windows пока не проверены

## Как работает сокращение токенов

### Слой 1: компактный режим

Убирает комментарии, пустые строки и пробелы в конце строк, сохраняя «магические» комментарии (`// @ts-ignore`, `// eslint-disable-*`).

До:
```typescript
// This function calculates the total price
// including tax and shipping
function calculateTotal(
  items: CartItem[],      // shopping cart items
  taxRate: number,        // local tax rate
): number {
  let total = 0;

  // Sum up item prices
  for (const item of items) {
    total += item.price * item.quantity;
  }

  // Apply tax
  total = total * (1 + taxRate);

  return total;
}
```

После:
```typescript
function calculateTotal(
  items: CartItem[],
  taxRate: number,
): number {
  let total = 0;
  for (const item of items) {
    total += item.price * item.quantity;
  }
  total = total * (1 + taxRate);
  return total;
}
```

### Слой 2: обрезка контекста

`get_context` не возвращает весь файл. Он возвращает запрошенный диапазон строк плюс `contextLines` строк выше и ниже него (по умолчанию 5, максимум 200), а затем применяет к этому фрагменту компактный режим. `_meta.reduction` сравнивает результат со всем файлом, а `_meta.layers` перечисляет, что было применено (`compact`, `prune`).

Обрезка выполняется только по диапазону строк: она не идёт по вызывающим и вызываемым. Чтобы прочитать то, что вызывает функция, или то, что вызывает её, запросите у `get_callees` / `get_callers` местоположения, а затем вызовите `get_context` для каждого.

### Слой 3: компактные списки

Ответ-список повторяет одно и то же в каждой строке: длинный путь к файлу, имена полей, значения, которые никогда не меняются. Компактная форма записывает каждое из них один раз: имена полей — в `columns`, путь — один раз на файл, относительно проекта. Это настоящий ответ `get_callers`:

```json
{
  "format": "compact",
  "columns": ["symbolId", "name", "kind", "line", "depth", "callLine", "callFile"],
  "files": [
    { "file": "src/indexing/file-watcher.ts", "rows": [["a182668c09c39b47", "scan", "method", 78, 1, 79, null]] }
  ],
  "_meta": { "originalTokens": 101, "compressedTokens": 54, "reduction": "46.5%", "compressed": true, "layers": ["group", "columns", "paths"] }
}
```

Ни одна строка не теряется и ничего не сворачивается в сводку; `symbolId`, относительный `file` и `line` можно сразу передавать в другие инструменты. `get_file_structure` и `list_dependencies` используют один плоский список `rows`. Если компактная форма не была бы меньше (пустой список, одна строка), возвращается обычная полезная нагрузка. Передайте `format: "full"` любому из этих инструментов, чтобы получить обычные объекты с абсолютными путями. Длинные списки запрашиваются страницами через `topK` и, для `get_references`, через `cursor`.

### Измерение экономии

Каждый ответ инструмента, кроме `index_status`, содержит блок `_meta` с фактической экономией токенов:

```json
{
  "_meta": {
    "originalTokens": 4782,
    "compressedTokens": 190,
    "reduction": "96.0%",
    "compressed": false,
    "layers": ["prune"]
  }
}
```

Этот пример — настоящий вызов `get_context` (±5 строк по умолчанию, компактный режим) для файла в 514 строк: фрагмент уже уплотнён самим инструментом, поэтому в списке только слой `prune`, а `compressed: false` означает, что компрессору ответов больше нечего было убирать. Поле `_meta.reduction` отсчитывается от исходного числа токенов всего файла и показывает реальную сквозную экономию. Ответы, которые не стали бы меньше, возвращаются как есть с `reduction: "0.0%"`; отрицательным это значение не бывает. Проверить, сколько именно Hesman экономит на ваших реальных задачах, можно по `_meta.reduction` в ответе любого инструмента.

## Установка и настройка

### Предварительные требования

- **Node.js** ≥ 20.0.0
- **npm** (или pnpm / yarn)

### Установка из исходного кода

Это способ, который работает сегодня.

```bash
git clone https://github.com/ocsen-hoc-code/hesman-mcp.git
cd hesman-mcp
npm install
npm run download:parsers   # Скачать WASM-парсеры Tree-sitter
npm run build              # Скомпилировать TypeScript
npm link                   # Необязательно: сделать `hesman` доступным в PATH
```

Без `npm link` используйте `node /path/to/hesman-mcp/dist/index.js` везде, где в этом README написано `hesman`.

### Установка из npm (после публикации пакета)

Пакета `hesman-mcp` пока нет в реестре npm. Когда он появится:

```bash
npx -y hesman-mcp setup     # без установки: клиенты запускают Hesman через npx
npm install -g hesman-mcp   # или глобальная установка, которая добавляет `hesman` в PATH
```

### Регистрация в AI-агентах

```bash
hesman setup                         # список клиентов, найденных на этой машине, с отметками
hesman setup --yes                   # без вопросов: настроить все обнаруженные клиенты
hesman setup --client cursor vscode  # настроить конкретные клиенты
hesman setup --dry-run --all         # показать точное изменение для каждого клиента, ничего не записывая
hesman remove                        # отмена: снова убрать Hesman из всех клиентов
```

| Клиент | `--client` | Что меняет `hesman setup` (область user) | `--scope project` |
|---|---|---|---|
| Claude Code | `claude-code` | выполняет `claude mcp add --scope user hesman -- <launch command>`; без CLI правит `~/.claude.json` | `.mcp.json` |
| Claude Desktop | `claude-desktop` | `claude_desktop_config.json` | — |
| OpenAI Codex CLI | `codex` | выполняет `codex mcp add hesman -- <launch command>`; без CLI правит `~/.codex/config.toml` | `.codex/config.toml` |
| Cursor | `cursor` | `~/.cursor/mcp.json` | `.cursor/mcp.json` |
| Google Antigravity | `antigravity` | `~/.gemini/config/mcp_config.json` | `.agents/mcp_config.json` |
| VS Code (Copilot) | `vscode` | `mcp.json` в пользовательском каталоге VS Code | `.vscode/mcp.json` |
| Gemini CLI | `gemini-cli` | `~/.gemini/settings.json` | `.gemini/settings.json` |
| Windsurf | `windsurf` | `~/.config/devin/mcp_config.json` | — |

- Затрагивается только запись `hesman`. Изменяемый файл сначала копируется в `<file>.hesman.bak`, и `hesman remove` восстанавливает его байт в байт, если за это время в нём больше ничего не изменилось.
- В записи нет пути к проекту: Hesman находит проект сам (см. ниже). Два исключения: у **Claude Desktop** нет рабочей области, поэтому его запись закрепляет один проект (текущий каталог или `--project-root <path>`), а **Cursor** получает `--project-root ${workspaceFolder}` только в области project (в глобальном `~/.cursor/mcp.json` эта переменная может оказаться вашим домашним каталогом, поэтому глобальная запись не называет проект).
- Для **Antigravity** и **Windsurf** не задокументировано, как проект передаётся серверу; `hesman setup` выводит примечание с просьбой проверить это после первого запуска.
- Конфигурационные файлы с комментариями (JSONC) не редактируются: `hesman setup` сообщает о них и оставляет нетронутыми.
- `hesman install --agent <name>` по-прежнему работает как устаревший псевдоним для `hesman setup --client <name> --yes`.

После настройки перезапустите клиент, и Hesman будет доступен как MCP-сервер.

### Правила использования для агентов (opt-in)

Установленный MCP-сервер — ещё не используемый MCP-сервер: агенты часто продолжают тянуться к grep и чтению файлов целиком. `hesman setup --rules` дополнительно записывает короткий блок (14 строк) в файл инструкций, который каждый выбранный клиент читает в **текущем проекте**; в блоке сказано, какой инструмент Hesman отвечает на какой вопрос. Меняет ли это частоту, с которой агент вызывает инструменты, пока не измерялось.

```bash
hesman setup --client claude-code codex --rules   # запускать внутри проекта
hesman setup --all --rules --dry-run              # показать блок и файлы, ничего не записывая
hesman remove                                     # заодно снова удаляет блок
```

| Клиент | Файл инструкций (относительно проекта) |
|---|---|
| Claude Code | `CLAUDE.md` |
| OpenAI Codex CLI, Windsurf | `AGENTS.md` |
| Gemini CLI, Google Antigravity | `GEMINI.md` |
| Cursor | `.cursor/rules/hesman.mdc` (собственный файл правил, `alwaysApply: true`) |
| VS Code (Copilot) | `.github/copilot-instructions.md` |
| Claude Desktop | нет: он не читает файлы проекта, поэтому пропускается с примечанием |

- **Opt-in.** Без `--rules` ничего не записывается. В терминале без `--yes` setup спрашивает один раз, и ответ по умолчанию — «Нет».
- Блок находится между `<!-- hesman:rules:start -->` и `<!-- hesman:rules:end -->`. Повторный запуск setup заменяет его на месте; текст за пределами маркеров никогда не меняется, а файл, общий для двух клиентов, получает блок один раз.
- `hesman remove` удаляет ровно этот блок и возвращает файл байт в байт; файл, который создал Hesman и в котором больше ничего нет, удаляется. Запускайте команду в том же проекте (или передайте `--project-root <path>` — его принимает и `setup --rules`).
- Эти файлы обычно коммитятся в git и используются всей командой. Setup перечисляет изменённые им файлы, чтобы вы могли просмотреть их (`git diff`) и решить, коммитить ли.

### Команда запуска

`hesman setup --command auto|npx|global|absolute` определяет, что именно будут запускать клиенты. Setup никогда не обращается к сети.

| `--command` | Записываемая запись | Что требуется |
|---|---|---|
| `npx` | `npx -y hesman-mcp@<major>` | пакет в npm (пока не опубликован) и `npx` в PATH клиента; переживает обновления Node |
| `global` | `hesman` | глобальная установка (или `npm link`) в PATH клиента |
| `absolute` | `/path/to/node /path/to/hesman-mcp/dist/index.js` | в PATH ничего не нужно; после смены версии Node или перемещения Hesman запустите `hesman setup` ещё раз |

`auto` (значение по умолчанию) смотрит на то, как был запущен работающий Hesman:

1. запущен через `npx` (работает из каталога кеша `_npx`) → `npx`;
2. `hesman` в PATH — это та же самая установка (с разрешением символических ссылок) → `global`;
3. всё остальное (рабочая копия исходников, локальный `node_modules`, отсутствие в PATH) → `absolute`.

Десктопные приложения (Claude Desktop, Cursor, Antigravity, VS Code, Windsurf), открытые из Dock или лаунчера, не получают PATH вашей оболочки. На macOS и Linux, когда `auto` выбирает `npx` или `hesman`, а эта команда или `node` находится не в стандартном системном каталоге (`/usr/bin`, `/bin`, `/usr/sbin`, `/sbin`, `/usr/local/bin`, плюс `/opt/homebrew/bin` на macOS и `/snap/bin` на Linux) — обычная ситуация с nvm, fnm, volta или asdf, — такие клиенты получают вместо этого запись `absolute` с примечанием о том, что после смены версии Node нужно снова запустить `hesman setup`. Терминальные клиенты (Claude Code, Codex CLI, Gemini CLI) наследуют оболочку и сохраняют выбранную команду. Явно заданный `--command npx|global` записывается как указано для каждого клиента — с предупреждением там, где десктопное приложение может не найти команду.

### Ручная настройка MCP

Добавьте это в конфигурационный файл MCP вашего агента (VS Code использует `"servers"` вместо `"mcpServers"` и требует `"type": "stdio"` в записи; Codex использует TOML-таблицу `[mcp_servers.hesman]`):

```json
{
  "mcpServers": {
    "hesman": {
      "command": "hesman",
      "args": ["--project-root", "/path/to/your/project"],
      "env": {}
    }
  }
}
```

`--project-root` необязателен; см. ниже. Для `"command": "hesman"` нужно, чтобы `hesman` был в том PATH, который видит клиент; иначе используйте `"command": "/path/to/node"` и `"/path/to/hesman-mcp/dist/index.js"` в качестве первого аргумента (см. [Команда запуска](#команда-запуска)).

### Как Hesman выбирает проект

Один процесс сервера индексирует один проект. Он выбирается в таком порядке:

1. **Явно заданный корень** — `--project-root <path>`, `HESMAN_PROJECT_ROOT` или `projectRoot` в `hesman.config.json`. Всегда имеет приоритет.
2. **Папки рабочей области MCP-клиента** — если клиент поддерживает возможность MCP `roots`, Hesman после рукопожатия запрашивает у него список папок и индексирует первую (остальные папки записываются в лог, но не индексируются). Когда позже клиент сообщает другую папку, Hesman переключается на неё.
3. **Рабочий каталог** — ближайший каталог, начиная с рабочего каталога сервера и выше, в котором есть каталог системы контроля версий (`.git`, `.hg`, `.svn`, `.jj`) или манифест проекта (`package.json`, `go.mod`, `pyproject.toml`, `Cargo.toml`, …).
4. **Проекта нет** — сервер всё равно запускается и перечисляет свои инструменты, но каждый инструмент возвращает ошибку `NO_PROJECT` с объяснением, как задать корень.

Домашний каталог и его родительские каталоги никогда не выбираются автоматически (шаги 2 и 3), так что глобальная запись MCP, запущенная из `~`, не станет обходить весь ваш диск. Индекс хранится в `.hesman/` внутри выбранного проекта.

## Удаление

Hesman хранит данные в четырёх местах. Удаляйте их в таком порядке: первые два шага требуют команды `hesman`.

**1. Уберите Hesman из своих AI-клиентов**

```bash
hesman remove --dry-run        # показать, что будет удалено, ничего не записывая
hesman remove                  # удалить запись hesman из каждого клиента, где она есть (область user)
hesman remove --scope project  # запускать внутри проекта, настроенного с --scope project
```

`hesman remove` удаляет только запись `hesman` и, если вы использовали `hesman setup --rules`, блок между `<!-- hesman:rules:start -->` и `<!-- hesman:rules:end -->` в файлах инструкций проекта; всё остальное в этих файлах остаётся как было. После этого перезапустите клиенты. Файл `<config>.hesman.bak` рядом с конфигурацией клиента — это резервная копия, которую Hesman сделал перед последней правкой; удалите его, когда он вам больше не нужен.

**2. Удалите индекс каждого проекта**

```bash
cd /path/to/project
hesman clean --dry-run   # показать каталог и его размер
hesman clean --force     # удалить .hesman/ (индекс, векторы, логи, журнал вызовов инструментов)
```

Повторите для каждого проекта, в котором использовался Hesman, или удалите каталог `.hesman/` проекта вручную. Если вы задали `HESMAN_DATA_DIR` или `--data-dir`, данные лежат в этом каталоге.

**3. Удалите кеш грамматик**

Грамматики, загруженные по запросу, хранятся для каждого пользователя отдельно, вне проекта. Удалите каталог `hesman` в первом месте, которое подходит:

| Настройка / платформа | Каталог для удаления |
|---|---|
| Задан `HESMAN_CACHE_DIR` | `$HESMAN_CACHE_DIR/hesman` |
| Задан `XDG_CACHE_HOME` | `$XDG_CACHE_HOME/hesman` |
| macOS | `~/Library/Caches/hesman` |
| Windows | `%LOCALAPPDATA%\hesman` |
| Linux и прочие | `~/.cache/hesman` |

`hesman grammars list` выводит точный путь к каталогу кеша. Если ни одна грамматика по запросу никогда не загружалась, каталога не существует.

**4. Удалите программу**

```bash
# установлено из исходников
npm unlink -g hesman-mcp   # только если вы выполняли `npm link`
rm -r /path/to/hesman-mcp  # клонированный репозиторий

# установлено из npm (после публикации пакета)
npm uninstall -g hesman-mcp
```

Модель эмбеддингов хранится внутри собственного `node_modules` пакета, поэтому исчезает вместе с программой. Нигде за пределами перечисленных мест ничего не записывается: ни фонового сервиса, ни системной конфигурации.

## Справочник инструментов

Hesman предоставляет **11 инструментов** через транспорт MCP stdio. Каждый ответ инструмента, кроме `index_status`, содержит блок `_meta` с экономией токенов (`impact_analysis` также возвращает собственный `_summary` затронутых файлов).

### Навигация по коду

| Инструмент | Что делает | Основные параметры |
|---|---|---|
| `find_symbol` | Находит символы по имени — точное, нечёткое совпадение или совпадение по префиксу | `name`, `kind`, `matchMode`, `topK` |
| `get_file_structure` | Возвращает иерархическое дерево всех символов файла | `filePath`, `includeNested` |
| `get_references` | Находит все места использования символа в кодовой базе | `symbolId`, `referenceKind`, `topK`, `cursor` |
| `get_context` | Возвращает уплотнённый код вокруг указанного места | `filePath`, `startLine`, `contextLines`, `mode` |

### Граф вызовов

| Инструмент | Что делает | Основные параметры |
|---|---|---|
| `get_callers` | Находит все функции, вызывающие данный символ (на глубину до 3 уровней) | `symbolId`, `maxDepth`, `topK` |
| `get_callees` | Находит все функции, вызываемые данным символом (на глубину до 3 уровней) | `symbolId`, `maxDepth`, `topK` |

### Анализ

| Инструмент | Что делает | Основные параметры |
|---|---|---|
| `impact_analysis` | Распределяет по категориям то, что сломается при изменении символа (переименование/удаление/изменение сигнатуры) | `symbolId`, `changeType` |
| `list_dependencies` | Показывает, что импортирует файл или кто импортирует из него | `filePath`, `direction` |
| `semantic_search` | Ищет код по описанию на естественном языке | `query`, `topK`, `language`, `kind` |
| `find_pattern` | Ищет по структурному шаблону с именованными захватами (`$NAME`, `$$$ARGS`) | `pattern`, `language`, `topK` |

### Статус

| Инструмент | Что делает |
|---|---|
| `index_status` | Сообщает о состоянии индексации: число файлов, число символов, статус хранилищ, файлы в очереди, прогресс первоначальной фоновой индексации |

Полные схемы входных и выходных данных с примерами см. в **[docs/TOOLS.md](../TOOLS.md)**.

## Конфигурация

Создайте `hesman.config.json` в корне проекта (все поля необязательны):

```json
{
  "projectRoot": ".",
  "workers": 0,
  "watchMode": true,
  "languages": ["*"],
  "ignore": ["node_modules/**", "dist/**", ".git/**", "legacy/**"],
  "semanticSearch": {
    "enabled": true,
    "defaultTopK": 10,
    "maxTopK": 50,
    "embeddingModel": "Xenova/all-MiniLM-L6-v2"
  },
  "logLevel": "info",
  "dataDir": ".hesman",
  "grammars": { "offline": false }
}
```

> **Символические ссылки при индексации пропускаются.** Сканер проекта и наблюдатель за файлами никогда не переходят по символическим ссылкам (на файлы или каталоги). Это предотвращает бесконечные циклы (например, `loop -> .`), не пускает в индекс код за пределами проекта и исключает дублирование символов. Чтобы проиндексировать код, на который ведёт ссылка, укажите в `projectRoot` реальный каталог.

### Приоритет конфигурации

Настройки определяются в таком порядке (более поздние переопределяют более ранние):

1. **Значения по умолчанию** — встроены в Hesman
2. **`hesman.config.json`** — конфигурационный файл уровня проекта
3. **Переменные окружения** — например, `HESMAN_WORKERS=4`
4. **Флаги CLI** — например, `--workers 4`

### Переменные окружения

| Переменная | Эквивалент | Описание |
|---|---|---|
| `HESMAN_PROJECT_ROOT` | `--project-root` | Путь к индексируемому проекту |
| `HESMAN_WORKERS` | `--workers N` | Число потоков-воркеров (0 = автоопределение) |
| `HESMAN_LOG_LEVEL` | `--log-level` | Одно из: trace, debug, info, warn, error |
| `HESMAN_DATA_DIR` | `--data-dir` | Каталог для данных индекса (по умолчанию: `.hesman`) |
| `HESMAN_WATCH_MODE` | `--watch-mode` | Включить/выключить отслеживание файлов (true/false) |
| `HESMAN_GRAMMARS_OFFLINE` | — | `1` или `true`: никогда не скачивать грамматики (ключ конфигурации `grammars.offline`) |
| `HESMAN_CACHE_DIR` | — | Каталог, в котором лежит пользовательский кеш грамматик (`<dir>/hesman/grammars/`) |

### Флаги CLI

| Флаг | Описание |
|---|---|
| `--project-root <path>` | Индексируемый проект (по умолчанию определяется автоматически, см. [Как Hesman выбирает проект](#как-hesman-выбирает-проект)) |
| `--workers <N>` | Число потоков-воркеров (0 = авто) |
| `--log-level <level>` | Уровень логирования |
| `--data-dir <path>` | Путь к каталогу данных |
| `--watch-mode` | Включить отслеживание файлов |
| `--no-watch` | Отключить отслеживание файлов |
| `--no-semantic` | Отключить семантический поиск |
| `--batch-size <N>` | Число файлов в одном пакете индексации |

Таблица выше генерируется из реестра языков (`npx tsx scripts/generate-language-matrix.ts`; тест падает, если она устарела). Грамматики с пометкой *в комплекте* поставляются внутри пакета, поэтому работают без сети.

**Грамматики по запросу.** Грамматик с пометкой *по запросу* в пакете нет. Когда в проекте впервые встречаются файлы такого языка, они сразу индексируются как текст, а сервер в фоне скачивает грамматику (0,3–11,4 МБ на грамматику, со страницы релизов собственного репозитория грамматики на GitHub); когда она получена, файлы переиндексируются уже с символами. Каждая грамматика закреплена по URL, размеру и sha256 в поставляемом `grammars.json`; загрузка, которая не совпадает, отбрасывается, и файлы остаются текстом. Грамматики кешируются для каждого пользователя отдельно, вне проекта: `HESMAN_CACHE_DIR`, иначе `XDG_CACHE_HOME`, иначе `~/Library/Caches` (macOS), `%LOCALAPPDATA%` (Windows) или `~/.cache`, в подкаталоге `hesman/grammars/`.

- **Отключить загрузки:** задайте `HESMAN_GRAMMARS_OFFLINE=1` или `"grammars": { "offline": true }` в `hesman.config.json`. Тогда Hesman не делает сетевых запросов за грамматиками; файлы языков с грамматикой по запросу остаются на уровне text, если грамматика ещё не в кеше.
- **Заранее наполнить кеш:** `hesman grammars install scala r` или `hesman grammars install --all` (46,9 МБ); на машине без доступа к сети скопируйте туда файлы `.wasm` и выполните `hesman grammars install --from <directory>`. `hesman grammars list` показывает, что идёт в комплекте, что в кеше и что доступно. См. [docs/CLI.md](../CLI.md#hesman-grammars).
- **Посмотреть, чего не хватает:** `index_status` перечисляет для каждого языка его уровень (`deep`, `structural` или `text`), число файлов и то, идёт ли его грамматика в комплекте, лежит в кеше или отсутствует, и почему.

`grammars.json` также закрепляет 17 грамматик, для которых пока нет запроса символов (Haskell, Zig, Julia, Perl, Objective-C, Odin, Luau, Starlark, HTML, CSS, JSON, YAML, TOML, XML, Markdown, HCL, Make). Их можно установить командой `hesman grammars install`, но Hesman их пока не использует: файлы этих языков индексируются как текст, а их грамматики никогда не скачиваются автоматически.

Что уровни означают сегодня:

- **deep** — определения (функции, классы, методы, константы, ...) плюс отношения `calls`, так что у `get_callers`, `get_callees`, `get_references` и `impact_analysis` есть граф вызовов. Вызовы читаются из синтаксического дерева каждого языка (его выражения вызова, `new X(...)`, вызовы без скобок в Ruby и Bash) и связываются по имени: сначала собственный файл вызывающего, затем файлы, которые он импортирует, его каталог и весь проект; имя, которое остаётся неоднозначным, не связывается вовсе, вместо того чтобы связываться с каждым кандидатом. Вызов связывается с определением, а не с объявлением без тела (прототип C/C++, метод интерфейса или абстрактный метод), а `new X(...)` — с классом `X`, а не с одним из его конструкторов. Типы не выводятся, поэтому метод, вызванный на интерфейсе с несколькими реализациями, остаётся несвязанным, а метод Ruby, вызванный без аргументов и скобок, не распознаётся как вызов. Отношения импорта есть для TypeScript/JavaScript, Python, Go, C/C++ (`#include "..."`) и Ruby (`require`, `require_relative`); отношения `extends` / `implements` — только там, где в языке пишут `class X extends Y` или `class X implements Y`.
- **structural** — только определения. Ни одного языка из комплекта на этом уровне больше нет. Языки с грамматикой по запросу относятся к structural, потому что используется только их upstream-запрос символов: для них нет правила видимости (каждое определение считается экспортируемым) и нет извлечения вызовов.
- **text** — символов нет; см. «Text tier» в [docs/TOOLS.md](../TOOLS.md).

Агенту не обязательно знать эту таблицу: когда `get_callers`, `get_callees`, `get_references` или `impact_analysis` спрашивают о символе языка без графа вызовов, ответ вместе с пустым списком содержит `note` вида `call graph not available for r (symbols only)`, чтобы пустой ответ не был принят за «это никем не используется».

Виды символов следуют собственному tags-запросу каждой грамматики, поэтому некоторые из них грубее, чем в самом языке: методы PHP и Kotlin — это `function`, перечисления Rust и Swift и интерфейсы Kotlin — `class`, псевдонимы типов Rust — `class`. Чтобы добавить язык, нужны грамматика, tags-запрос, небольшой профиль и одна запись в реестре языков (`src/parsers/languages.ts`) — пошаговые инструкции см. в [руководстве для контрибьюторов](../CONTRIBUTING.md).

## Архитектура

```
                         ┌──────────────────────────────────────┐
                         │         AI Agent (Claude, etc.)       │
                         │              │  MCP stdio              │
                         └──────────────┼─────────────────────────┘
                                        │
                         ┌──────────────┼─────────────────────────┐
                         │       Hesman MCP Server                │
                         │              │                          │
                         │   ┌──────────┴──────────────────────┐  │
                         │   │      Token Reduction Pipeline    │  │
                         │   │  ┌────────────────────────────┐  │  │
                         │   │  │ 1. Compact Mode            │  │  │
                         │   │  │    Strip comments/blanks    │  │  │
                         │   │  │ 2. Context Pruning         │  │  │
                         │   │  │    A line range, not a file │  │  │
                         │   │  │ 3. Compact Lists           │  │  │
                         │   │  │    Columns, grouped by file │  │  │
                         │   │  └────────────────────────────┘  │  │
                         │   └───────────────────────────────────┘  │
                         │                                          │
                         │   ┌──────────┐ ┌──────────┐ ┌─────────┐ │
                         │   │  SQLite  │ │   ZVec   │ │ Worker  │ │
                         │   │  Store   │ │  Vector  │ │  Pool   │ │
                         │   │ (symbols)│ │ (search) │ │ (index) │ │
                         │   └────┬─────┘ └────┬─────┘ └────┬────┘ │
                         │        │            │            │       │
                         │   ┌────┴────────────┴────────────┴────┐  │
                         │   │     File Watcher (chokidar)       │  │
                         │   └───────────────────────────────────┘  │
                         └──────────────────────────────────────────┘
```

**Основной конвейер данных:** изменения файлов (chokidar) → разбор Tree-sitter (AST + символы) → индекс SQLite + эмбеддинги ZVec → компактные ответы MCP

**Ключевые проектные решения:**
- **Нет зависимости от LSP** — Tree-sitter даёт не зависящий от языка разбор без запуска языковых серверов
- **Инкрементальная индексация по хешу содержимого** — файлы разбираются заново только при изменении SHA-256
- **Сжатие на уровне ответа** — исходные данные остаются нетронутыми; сжатие применяется на границе ответа
- **Одна база данных SQLite на проект** — даже в монорепозиториях все пакеты используют одно хранилище с изоляцией по `file_path`

Полный документ по архитектуре, включая зависимости модулей, схемы хранилищ и устройство пула воркеров, см. в **[docs/ARCHITECTURE.md](../ARCHITECTURE.md)**.

## Настройка окружения для разработки

### Предварительные требования

- **Node.js** ≥ 20.0.0
- **npm** ≥ 10

### Начало работы

```bash
# Клонирование и установка
git clone https://github.com/ocsen-hoc-code/hesman-mcp.git
cd hesman-mcp
npm install

# Скачать WASM-парсеры Tree-sitter
npm run download:parsers

# Запуск в режиме разработки (горячая перезагрузка)
npm run dev

# Сборка для продакшена
npm run build
```

### Качество кода

```bash
npm run typecheck    # Проверка типов TypeScript
npm run lint         # ESLint
npm run format       # Форматирование Prettier
```

### Запуск тестов

```bash
npm test                  # Запустить все тесты (модульные + интеграционные)
npm run test:watch        # Режим наблюдения для разработки
npm run test:e2e          # Сквозные тесты (запускают полноценный сервер)
npm run test:perf         # Бенчмарки производительности
```

### Пороги производительности

`npm run test:perf` завершается с ошибкой, если бенчмарк хуже своего порога (`tests/perf/thresholds.ts`). Это пределы, проверенные на macOS-машине сопровождающего на фикстурах репозитория, а не гарантии для любого проекта; `semantic_search` измеряется без эмбеддинга запроса.

| Бенчмарк | Порог |
|---|---|
| `find_symbol` (точный) | < 1 мс |
| `find_symbol` (нечёткий) | < 5 мс |
| `semantic_search` | < 10 мс |
| `get_references` | < 5 мс |

### Измерения на этом репозитории

`node scripts/measure.mjs` запускает собранный сервер через stdio, позволяет ему проиндексировать чистый экспорт этого репозитория (502 файла: 350 с символами, 152 как текст; 7 700 символов, 27 372 связи) и вызывает каждый инструмент 100 раз через MCP. Измерено 2026-10-13 на Apple M3 Pro (11 ядер, 18 ГБ), macOS, Node 24. Ваши цифры зависят от машины и проекта; запустите скрипт, чтобы получить свои.

| Запуск, индекс и память | Семантический поиск включён | `--no-semantic` |
|---|---:|---:|
| Ответ на рукопожатие MCP через | 0,4 с | 0,2 с |
| Индекс готов через | 70,2 с | 2,4 с |
| Индекс на диске | 46,2 МБ | 22,1 МБ |
| Память при рукопожатии | 286 МБ | 195 МБ |
| Память сразу после индексации | 673 МБ | 426 МБ |
| Память в простое (через 35 с после последнего вызова) | 545 МБ | 303 МБ |

Сервер отвечает на вызовы инструментов во время индексации; при включённом семантическом поиске почти все 70 секунд уходят на вычисление 5 760 эмбеддингов на CPU. Память — это физический footprint процесса, то есть число, которое показывает Мониторинг активности. Потоки парсера запускаются только во время индексации (по умолчанию не более четырёх) и освобождаются после 30 секунд простоя.

| Инструмент | Вызов | Медиана | Исходные токены | Токены в ответе | Экономия |
|---|---|---:|---:|---:|---:|
| `get_context` | одна функция, ±5 строк | 0,39 мс | 4 782 | 190 | 96,0% |
| `get_context` | одна функция, ±40 строк | 0,46 мс | 4 782 | 970 | 79,7% |
| `get_references` | ссылки на `indexProject` | 0,29 мс | 3 026 | 854 | 71,8% |
| `get_callers` | вызывающие `indexProject` | 0,24 мс | 1 244 | 373 | 70,0% |
| `get_callees` | вызываемые из `indexProject` | 0,15 мс | 387 | 132 | 65,9% |
| `find_symbol` | префикс `index`, 20 результатов | 0,38 мс | 2 326 | 1 369 | 41,1% |
| `impact_analysis` | удаление `indexProject` | 0,39 мс | 3 498 | 2 116 | 39,5% |
| `get_file_structure` | один файл с исходным кодом | 0,34 мс | 3 474 | 2 270 | 34,7% |
| `list_dependencies` | импорты одного файла | 0,11 мс | 572 | 374 | 34,6% |
| `find_symbol` | точное имя, 1 результат | 0,14 мс | 214 | 197 | 7,9% |
| `find_pattern` | `console.$M($$$A)` в TypeScript | 38,4 мс | 2 112 | 2 112 | 0,0% |
| `semantic_search` | один запрос на естественном языке | 2,75 мс | 3 880 | 3 880 | 0,0% |

«Исходные токены» — это payload в виде обычных JSON-объектов с абсолютными путями (для `get_context` — весь файл); токены оцениваются как по четыре символа на токен. Задержка — то, что видит клиент на один вызов, включая обмен по MCP. `semantic_search` включает получение эмбеддинга запроса.
